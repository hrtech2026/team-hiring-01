# Формализация требований

## User Stories

### US-01. Интервью по темам роли

Как руководитель,
я хочу отвечать на вопросы системы по темам роли своими словами,
чтобы передать реальные задачи роли без самостоятельного написания текста вакансии и долгой переписки с HR.

**Уровень:** L2 (вопросы ИИ), L0 (ответы) · **TO-BE:** `INT`, `ANS` · **Зависит от:** US-09, US-12

Критерии приёмки:

```gherkin
Given руководитель сообщил о потребности в найме (REQ), When система запускает интервью, Then ИИ задаёт вопросы по темам: задачи, стек, нагрузка, процессы, команда
Given вопрос по теме задан, When руководитель отвечает «не знаю», Then система принимает ответ без сообщения об ошибке
Given руководитель ответил «не знаю» по теме, When система сохраняет ответ, Then тема отмечена как нераскрытая с указанием, кто и когда ответил «не знаю»
Given ответ руководителя содержит ФИО или контакты, When система передаёт ответ в ИИ-модель, Then ФИО и контакты в переданном тексте замаскированы
Given достигнуто максимальное число раундов (MAX_ROUNDS), When по обязательным темам остаются нераскрытые, Then система прекращает задавать вопросы
Given ИИ-модель недоступна, When руководитель начинает интервью, Then система сообщает руководителю, что ИИ недоступен
Given ИИ-модель недоступна, When руководитель сообщил о потребности в найме, Then HR выполняет шаги 2–5 вручную, как в AS-IS
```

### US-02. Профиль роли и проверка полноты тем

Как HR,
я хочу видеть в профиле роли, какие обязательные темы остались нераскрытыми,
чтобы не готовить черновик вакансии по недостающим сведениям.

**Уровень:** L2 + правило · **TO-BE:** `RUL`, `BK1` · **Зависит от:** US-01

Критерии приёмки:

```gherkin
Given интервью завершено и все темы из MANDATORY_TOPICS раскрыты, When правило проверяет полноту, Then профиль роли передаётся руководителю на подтверждение (H1)
Given часть обязательных тем нераскрыта и раунды остались, When правило проверяет полноту, Then система возвращается к INT (BK1)
Given система вернулась к INT (BK1), When ИИ формирует вопросы, Then вопросы задаются только по нераскрытым темам
Given ответ по обязательной теме — «не знаю», When правило проверяет полноту, Then тема считается нераскрытой
Given достигнут MAX_ROUNDS и часть обязательных тем нераскрыта, When правило проверяет полноту, Then профиль роли передаётся руководителю на H1, а не на BK1
Given профиль роли передан на H1 с нераскрытыми темами, When руководитель или HR открывает профиль, Then нераскрытые темы отмечены как «нераскрыта»
```

### US-03. Подтверждение профиля роли (H1)

Как руководитель,
я хочу подтвердить или поправить профиль роли до того, как по нему напишут вакансию,
чтобы в основу текста легли мои реальные требования, а не домысел системы.

**Уровень:** L2 · **TO-BE:** `H1` · **Зависит от:** US-02, US-09

Критерии приёмки:

```gherkin
Given профиль роли готов, When руководитель подтверждает профиль, Then система сохраняет версию профиля как подтверждённую
Given руководитель подтвердил профиль, When решение принято, Then система создаёт запись H1 в журнале в момент решения
Given руководитель правит пункт профиля, When подтверждает профиль, Then система сохраняет новую версию профиля
Given руководитель отклоняет предложение системы, When указывает причину, Then в профиле остаётся версия руководителя
Given руководитель отклонил предложение системы, When решение принято, Then запись журнала содержит отказ и причину
Given руководитель отклоняет предложение системы, When причина не указана, Then система не принимает отклонение
Given решение H1 не принято, When HR готовит вакансию к публикации, Then вакансия не получает статус «Разрешена к публикации» (см. US-08)
```

### US-04. Сверка черновика с профилем и предложение правок

Как HR,
я хочу видеть расхождения между черновиком и подтверждённым профилем с обоснованием по каждому,
чтобы не переносить в вакансию устаревшие требования из шаблона и не терять нужные.

**Уровень:** L2 · **TO-BE:** `DRAFT`, `CMP`, `CONF`, `SUG` · **Зависит от:** US-03, US-09

Критерии приёмки:

```gherkin
Given черновик загружен, When ИИ сравнивает черновик с профилем, Then сравнение выполняется только по требованиям, подтверждённым на H1
Given требование есть в черновике и отсутствует в профиле, When уверенность выше CONF_THRESHOLD и стоп-формулировок нет, Then система предлагает HR сохранить, изменить или удалить требование
Given система сформировала предложение, When HR открывает предложение, Then рядом указаны ссылка на ответ руководителя и фрагмент текста черновика
Given к предложению нельзя привязать источник, When система формирует результат, Then система не показывает это предложение
Given требование есть в профиле и отсутствует в черновике, When система формирует результат, Then пропущенное требование показано HR как расхождение
Given уверенность ниже CONF_THRESHOLD или найдена стоп-формулировка, When выполняется проверка CONF, Then система формирует сводку с вопросом (US-05) вместо предложения правки
```

### US-05. Сводка расхождения и вопрос руководителю

Как руководитель,
я хочу получать сводку и уточняющий вопрос, когда система не уверена или нашла рискованную формулировку,
чтобы решение принималось мной, а не подсказывалось готовой правкой.

**Уровень:** L1, после ответа руководителя — L2 · **TO-BE:** `CONF`, `SUM` · **Зависит от:** US-04

Критерии приёмки:

```gherkin
Given уверенность ниже CONF_THRESHOLD, When система формирует результат, Then руководитель видит расхождение и уточняющий вопрос
Given уверенность ниже CONF_THRESHOLD, When система формирует результат, Then система не показывает готовую правку
Given найдена стоп-формулировка и уверенность выше CONF_THRESHOLD, When система формирует результат, Then результат остаётся сводкой уровня L1, а не предложением правки
Given руководитель ответил на вопрос системы, When ответ получен, Then система предлагает сохранить, изменить или удалить требование с обоснованием (L2)
Given система показывает расхождение, When формирует сводку, Then сводка содержит повлиявшие признаки, использованные данные и то, что человеку стоит проверить
Given после правок повторная сверка не нашла расхождений, When формируется результат, Then система сообщает, что расхождений нет
Given система сообщила, что расхождений нет, When проходит H2, Then HR с руководителем подтверждают текст без правок
```

### US-06. Решение по расхождениям (H2) и повторная сверка

Как HR,
я хочу вместе с руководителем принять или отклонить каждое предложение и внести принятые правки,
чтобы согласование закрывалось одним общим решением вместо цепочки замечаний и возвратов.

**Уровень:** L2, для формулировок риска L1 · **TO-BE:** `H2`, `DF`, `FIX` · **Зависит от:** US-04, US-05

Критерии приёмки:

```gherkin
Given система показала предложения, When HR с руководителем принимают предложение, Then система создаёт запись H2 в журнале в момент решения
Given HR с руководителем отклоняют предложение, When указана причина, Then текст остаётся без изменений
Given HR с руководителем отклонили предложение, When решение принято, Then расхождение помечено «отклонено» с причиной
Given HR с руководителем отклонили предложение, When решение принято, Then система записывает отказ в журнал
Given есть принятые правки (DF = Да), When HR вносит их в черновик (FIX), Then система повторно сверяет новую версию черновика
Given найдена формулировка риска, When HR пытается закрыть пункт без решения, Then система не позволяет закрыть пункт без принятия или отклонения с причиной
Given HR с руководителем выбрали DF = Нет, When решение H2 записано, Then процесс переходит к H3
```

### US-07. Утверждение итогового текста (H3) и возврат на доработку

Как руководитель,
я хочу утвердить итоговый текст вакансии или вернуть его на доработку,
чтобы в публикацию ушла версия, содержание которой подтвердил я.

**Уровень:** L1 · **TO-BE:** `H3`, `DT`, `BK2` · **Зависит от:** US-06

Критерии приёмки:

```gherkin
Given последняя версия черновика прошла сверку, When руководитель утверждает текст, Then система создаёт запись H3 в журнале в момент решения
Given руководитель утвердил текст, When решение записано, Then процесс переходит к ADDQ
Given текст изменён после последней сверки, When руководитель пытается утвердить текст, Then система не позволяет утвердить его до новой сверки
Given руководитель отклоняет текст, When указывает причину, Then система возвращает вакансию HR на доработку (BK2)
Given руководитель отклонил текст, When решение принято, Then запись журнала содержит возврат и причину
Given решение H3 не принято, When HR готовит вакансию к публикации, Then вакансия не получает статус «Разрешена к публикации»
```

### US-08. Дополнительное согласование и публикация только человеком

Как HR,
я хочу публиковать вакансию только после H1–H3 и, если регламент предусматривает, после дополнительного согласования,
чтобы текст не ушёл кандидатам без содержательной и административной проверки.

**Уровень:** L1 · **TO-BE:** `ADDQ`, `ADD`, `DA`, `BK3`, `PUB` · **Зависит от:** US-07

Критерии приёмки:

```gherkin
Given записи H1, H2, H3 созданы и ADDQ = Нет, When HR открывает публикацию, Then система присваивает вакансии статус «Разрешена к публикации»
Given ADDQ = Да и решение DA не получено, When HR открывает публикацию, Then вакансия не получает статус «Разрешена к публикации»
Given согласующий вернул заявку (DA = Вернуть), When указал причину, Then система возвращает вакансию на H2 (BK3)
Given согласующий вернул заявку, When решение принято, Then запись журнала содержит возврат и причину
Given отсутствует хотя бы одна запись из H1–H3, When HR открывает публикацию, Then вакансия не получает статус «Разрешена к публикации»
Given вакансия получила статус «Разрешена к публикации», When HR не выполнил публикацию, Then система не публикует вакансию сама
Given HR опубликовал вакансию, When HR отметил публикацию в системе, Then система сохраняет запись о публикации со ссылкой на версию текста
Given интеграция системы с каналом публикации определена, When вакансию без статуса «Разрешена к публикации» передают в канал, Then канал не принимает вакансию
Given интеграция системы с каналом публикации не определена, When вакансия опубликована без статуса «Разрешена к публикации», Then сверка опубликованных вакансий с журналом выявляет нарушение
```

### US-09. Журнал решений

Как руководитель HR,
я хочу видеть запись по каждому решению H1–H3 с выводом системы и действием человека,
чтобы можно было проверить и оспорить любое решение.

**Уровень:** L3 · **TO-BE:** `LOG` · **Зависит от:** нет (обязателен для US-03, US-06, US-07, US-08)

Критерии приёмки:

```gherkin
Given человек подтвердил решение H1, H2 или H3, When система сохраняет решение, Then запись создаётся в момент решения, а не после публикации
Given человек отклонил предложение или вернул текст на доработку, When решение принято, Then система создаёт запись так же, как для принятия
Given система создаёт запись решения, When запись сохраняется, Then запись содержит поля decision_id, vacancy_id, decision_point, timestamp, actor_id, system_version, input_hash, draft_version_ref, answers_version_ref, features_used, model_output, confidence, human_action, override_reason
Given система создаёт запись решения, When считается input_hash, Then input_hash равен хешу пары «версия черновика и версия ответов интервью»
Given запись создана, When input_hash пересчитывают по сохранённым версиям, Then значение совпадает со значением в записи
Given запись создана, When пользователь открывает ссылки draft_version_ref и answers_version_ref, Then система показывает версии, на которых принято решение
Given запись создана, When любая роль пытается изменить или удалить запись, Then система отклоняет операцию
```

### US-10. Напоминания и эскалация

Как руководитель HR,
я хочу, чтобы при отсутствии решения на H1–H3 система напоминала ответственному и сообщала мне,
чтобы вакансия не простаивала и при этом не получала разрешение на публикацию без решения человека.

**Уровень:** L3 · **TO-BE:** эскалация по `H1`–`H3` · **Зависит от:** US-03, US-06, US-07, US-09

Критерии приёмки:

```gherkin
Given решение H1, H2 или H3 не принято, When истёк срок (SLA_H1, SLA_H2 или SLA_H3), Then ответственному уходит напоминание
Given напоминание отправлено, When решение по-прежнему не принято, Then руководитель HR получает уведомление
Given решение не принято, When идёт эскалация, Then вакансия не получает статус «Разрешена к публикации»
Given система отправила напоминание или уведомление, When отправка выполнена, Then система создаёт отдельную запись журнала об эскалации
Given запись об эскалации создана, When создаётся запись решения H1, H2 или H3, Then запись об эскалации не изменяется
Given руководитель HR получил уведомление, When решение не принято, Then система не принимает решение за отсутствующего человека
```

### US-11. Измерение показателей пилота

Как руководитель HR,
я хочу видеть M5 и M6 до и после внедрения и данные для M2–M4,
чтобы проверить, что время до утверждения не выросло, и вовремя отключить ИИ-часть, если стало хуже.

**Уровень:** L0 (данные), L3 (расчёт) · **TO-BE:** «План проверки (пилот)» · **Зависит от:** US-09

Критерии приёмки:

```gherkin
Given у вакансии есть отметки шагов REQ и H3, When считается M5, Then M5 равен числу рабочих дней от запроса до содержательного утверждения
Given вакансия прошла согласование, When считается M6, Then M6 равен числу повторных циклов согласования между людьми: возвратов BK2 и BK3 на вакансию
Given после правок (FIX) выполнена повторная ИИ-сверка, When считаются показатели, Then число повторных ИИ-сверок на вакансию считается отдельно и не входит в M6
Given данные для M2–M4 берутся из журнала вакансий и кадрового учёта, When показатель выводится, Then он выводится только суммарно, без фамилий
Given данные для M2–M4 берутся из журнала вакансий и кадрового учёта, When система их использует, Then данные читаются и не копируются в хранилище системы
Given исходных данных для показателя нет, When показатель запрашивается, Then система показывает «не измерено», а не ноль
Given M5 ухудшился или M6 вырос относительно базового уровня, When руководитель HR открывает показатели, Then ухудшение видно в сводке
```

### US-12. Отключение ИИ-части

Как руководитель HR,
я хочу отключить ИИ-часть для роли или перевести её на уровень L1 (только сводка),
чтобы при ухудшении качества или сроков процесс продолжал работать без ИИ.

**Уровень:** L0 · **TO-BE:** «Риски ИИ и контрмеры» (откат до L1), «Новое противоречие после внедрения» · **Зависит от:** US-09

Критерии приёмки:

```gherkin
Given руководитель HR отключил ИИ-часть для роли, When создаётся вакансия по этой роли, Then интервью и сверка выполняются без ИИ, как в AS-IS
Given ИИ-часть для роли отключена, When вакансия доходит до публикации, Then H3 остаётся обязательным
Given выбран откат до L1, When выполняется сверка, Then система показывает только сводки
Given выбран откат до L1, When выполняется сверка, Then система не предлагает правок
Given ИИ-часть отключена или переведена на L1, When действие выполнено, Then журнал содержит действие, автора и время
Given готова новая версия ИИ-модели, When её собираются включить, Then перед включением выполнена проверка на тестовых вакансиях
```

## Use Cases

### UC-01. Сбор и подтверждение профиля роли

| Поле | Значение |
|---|---|
| Актёры | Руководитель; HR (получатель профиля); система (ИИ и правила) |
| Предусловия | Руководитель имеет доступ к интерфейсу; ИИ-модель во внутреннем контуре доступна; заданы MANDATORY_TOPICS и MAX_ROUNDS |
| Триггер | Руководитель сообщает о потребности в найме (`REQ`) |

Основной сценарий (шаги 1–5 TO-BE):

1. Руководитель сообщает о потребности в найме (`REQ`).
2. Система через ИИ задаёт вопросы по темам: задачи, стек, нагрузка, процессы, команда (`INT`).
3. Руководитель отвечает своими словами (`ANS`); система маскирует ФИО и контакты до передачи ответа ИИ-модели.
4. ИИ собирает профиль роли; правило проверяет, раскрыты ли обязательные темы (`RUL`); все обязательные темы раскрыты.
5. Руководитель подтверждает или правит профиль (`H1`); система записывает решение в `decision_log`.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 3a | Руководитель отвечает «не знаю» по теме | Тема отмечается нераскрытой с указанием, кто и когда ответил; ответ принимается |
| 4a | Обязательные темы нераскрыты, раунды остались | Возврат `BK1` к шагу 2: вопросы только по нераскрытым темам |
| 4b | Обязательные темы нераскрыты, достигнут MAX_ROUNDS | Профиль передаётся на `H1` с отметкой нераскрытых тем, видимой руководителю и HR |
| 5a | Руководитель правит профиль | Система сохраняет новую версию профиля и записывает правку и автора в журнал |
| 5b | Руководитель отклоняет предложение системы | Требуется причина; остаётся версия руководителя; система записывает отказ и причину в журнал |
| 5c | Решение не принято в срок (SLA_H1) | Напоминание (L3), затем уведомление руководителя HR; каждая эскалация фиксируется отдельной записью; вакансия не получает статус «Разрешена к публикации» |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 2b | ИИ-модель недоступна или вернула ошибку | Процесс не блокируется: ИИ-часть отключена для вакансии, шаги 2–5 AS-IS выполняет HR вручную; факт фиксируется |

Постусловия: профиль роли подтверждён и сохранён отдельной версией; запись `H1` в журнале; HR может готовить черновик.

### UC-02. Сверка черновика с профилем и утверждение текста

| Поле | Значение |
|---|---|
| Актёры | HR; руководитель; система (ИИ и правила) |
| Предусловия | Выполнен `H1`, профиль подтверждён; заданы CONF_THRESHOLD и STOP_LIST |
| Триггер | HR подготовил черновик по профилю и шаблону (`DRAFT`) |

Основной сценарий (шаги 6–12 TO-BE):

1. HR готовит черновик по подтверждённому профилю (при наличии, по шаблону) и загружает версию (`DRAFT`).
2. ИИ сравнивает черновик с профилем, правила ищут стоп-формулировки (`CMP`).
3. Система проверяет, что уверенность выше порога и стоп-формулировок нет (`CONF`).
4. Система предлагает правку с обоснованием: что сохранить, изменить или удалить (`SUG`).
5. HR с руководителем принимают или отклоняют каждое предложение (`H2`); система записывает решение в журнал.
6. Если есть принятые правки (`DF` = Да), HR вносит их в черновик (`FIX`).
7. Система повторно сверяет новую версию (шаги 2–5); расхождений нет, `DF` = Нет.
8. Руководитель утверждает итоговый текст (`H3`); система записывает решение в журнал.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 2a | Расхождений нет | Система сообщает об этом; `H2` подтверждает текст без правок; переход к `H3` |
| 3a | Уверенность ниже порога или найдена стоп-формулировка | `SUM` (L1): сводка и вопрос руководителю; после ответа предложение правки (L2); решение остаётся за человеком |
| 5a | Все предложения отклонены | Текст не меняется, расхождения помечаются «отклонено» с причиной; переход к `H3` |
| 5b | Решение не принято в срок (SLA_H2) | Напоминание (L3), затем уведомление руководителя HR; каждая эскалация фиксируется отдельной записью; вакансия не получает статус «Разрешена к публикации» |
| 7a | Повторная сверка нашла новое расхождение | Повтор шагов 3–5, пока человек не выберет `DF` = Нет |
| 8a | Руководитель отклоняет текст (`DT` = Нет) | Возврат `BK2` к шагу 1: HR дорабатывает черновик; система записывает возврат и причину в журнал |
| 8b | Решение не принято в срок (SLA_H3) | Напоминание (L3), затем уведомление руководителя HR; каждая эскалация фиксируется отдельной записью; вакансия не получает статус «Разрешена к публикации» |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 2b | ИИ-модель недоступна | Сверка выполняется вручную, как в AS-IS (шаги 8–11); `H3` остаётся обязательным, статус «Разрешена к публикации» без него не присваивается |
| 4b | К предложению нельзя привязать источник | Система не показывает предложение |
| 8c | Текст изменён после последней сверки | `H3` недоступен до новой сверки |

Постусловия: итоговая версия текста прошла сверку и утверждена руководителем; записи `H2` и `H3` в журнале; версия системы и модели зафиксирована.

### UC-03. Дополнительное согласование и публикация

| Поле | Значение |
|---|---|
| Актёры | HR; согласующий (если предусмотрен); система |
| Предусловия | Записаны `H1`, `H2`, `H3`; утверждена версия текста, прошедшая сверку |
| Триггер | Руководитель утвердил итоговый текст (`H3`) |

Основной сценарий (шаги 13–15 TO-BE):

1. HR определяет, нужно ли дополнительное согласование по регламенту компании (`ADDQ`).
2. Дополнительное согласование не нужно: система присваивает вакансии статус «Разрешена к публикации».
3. HR публикует вакансию (`PUB`) и отмечает публикацию в системе.
4. Система сохраняет запись о публикации со ссылкой на версию текста.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 2a | Нужно дополнительное согласование (`ADDQ` = Да) | Согласующий проверяет заявку и условия (`ADD`); при одобрении (`DA` = Да) система присваивает статус «Разрешена к публикации», переход к шагу 3 |
| 2b | Согласующий возвращает заявку (`DA` = Вернуть) | Возврат `BK3` к `H2` (UC-02, шаг 5): система записывает причину в журнал |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 3b | Отсутствует хотя бы одно из решений `H1`–`H3` | Статус «Разрешена к публикации» не присваивается |
| 3c | Публикация вакансии средствами системы без человека | Не поддерживается: у системы нет операции публикации |

Постусловия: вакансия опубликована человеком; версия текста связана с записями `H1`–`H3`; цепочка решений доступна в журнале.

|---|---|---|

В 03 это отнесено на этап требований. Предложение команды, согласовать с ИТ и ИБ компании.

## Ограничения и допущения

Ограничения — не обсуждаются, это внешние данные.

| Ограничение | Источник |
|---|---|
| Система работает только с текстом вакансии и ответами руководителя о роли. Она не отбирает и не ранжирует кандидатов, не принимает решений о найме или отказе, не составляет профилей людей (оценок или характеристик руководителя, HR или кандидата) и не определяет эмоции по голосу или лицу. Причина: такие функции относятся к высокому риску по EU AI Act (Annex III, п. 4), а определение эмоций на работе запрещено (Art. 5(1)(f)) | `01_problem.md`, «Не входит в объём» (отбор, ранжирование, решения о найме); `03_tobe_architecture.md`, «Классификация по EU AI Act» (профилирование, эмоции) |
| Публикацию выполняет только человек; система не публикует | `01_problem.md`, «Не входит в объём»; `03_tobe_architecture.md`, `PUB` |
| Окончательное утверждение вакансии остаётся за человеком (`H3`) | `01_problem.md`, «Бизнес-цель» |
| Время до утверждения (M5) не увеличивается относительно базового процесса; доля релевантных откликов не ухудшается | `01_problem.md`, «Бизнес-цель» |
| Дополнительное согласование (шаг 14 AS-IS) остаётся без изменений и не заменяется системой | `03_tobe_architecture.md`, «Шаги процесса» |
| Уровень автоматизации не выше L1 для публикации и утверждения; L4 не применяется | `03_tobe_architecture.md`, «Уровни автоматизации» |
| Ответы руководителя, версии вакансии и журнал хранятся и обрабатываются только во внутреннем контуре компании; ИИ-модель работает внутри этого контура; внешние ИИ-сервисы не используются. Причина: в ответах руководителя могут встретиться персональные данные сотрудников (в `03` приведён пример: фамилии коллег), а в вакансиях — названия внутренних систем. ФИО и контакты маскируются до передачи ответа ИИ-модели | `03_tobe_architecture.md`, «Границы контура данных» и «Архитектура решения» (решение команды) |
| Данных реальной компании нет; базовые значения метрик не измерены, числовые пороги задаются на кейсе | `01_problem.md`, «Контекст», «Метрики успеха»; `02_asis_analysis.md`, «Оценка потерь» |

Допущения — проверяемы, подтверждение меняет архитектуру.

| Допущение | Кто подтвердит | Что меняется, если неверно |
|---|---|---|
| ИИ-модель внутри контура ведёт интервью и находит расхождения между текстом и ответами; допустимая доля пропущенных расхождений и ложных предупреждений задаётся до теста (допущение 4 из `01_problem.md`) | ИТ компании; команда на тестовых вакансиях | ИИ-часть остаётся на L0/L1 (структурированный опросник без ИИ-сверки), US-01, US-04, US-05 упрощаются |
| Руководитель отвечает на вопросы без роста M5 | Руководитель HR; пилот | ИИ-часть для роли отключается (US-12) |
| Пороги и число раундов подбираются на тестовых вакансиях | Команда | Меняется соотношение L2 и L1 (`SUG` и `SUM`) |
| Интеграция системы с каналом публикации (ATS, карьерный сайт) пока не определена. Без интеграции система присваивает статус «Разрешена к публикации», а запрет публикации без статуса обеспечивается регламентом компании и проверяется сверкой опубликованных вакансий с журналом | ИТ компании | При наличии интеграции канал сам не принимает вакансию без статуса; без неё контроль остаётся организационным (US-08) |
| Единица M6 в TO-BE — возврат между людьми (`BK2`, `BK3`); повторные ИИ-сверки считаются отдельно. Это сопоставимо с «циклом согласования» из AS-IS (шаги 8–12 в `02_asis_analysis.md`) | Команда (авторы `02`) | Если цикл в AS-IS определён иначе, сравнение M6 до и после нужно пересчитать |
| Срок хранения журнала 12 месяцев достаточен | Руководитель HR; ИБ | Меняются LOG_RETENTION и объём хранилища |
| Система вне высокого риска по EU AI Act (Annex III, п. 4); в `03` это названо допущением 7 из `01_problem.md` | Юрист; у команды нет доступа к юристу, поэтому допущение остаётся непроверенным | Добавляются требования Art. 9–15 и 26, меняется объём функций |
| Российские нормы (персональные данные, трудовое право, регулирование ИИ в найме) не разбирались | Юрист или ответственный за ПДн; у команды нет доступа, поэтому остаётся непроверенным | Добавляются требования к хранению, согласиям и аудиту |
| Данные для M2–M4 (журнал вакансий, кадровый учёт, причины ухода) доступны в суммарном виде | ИТ и HR компании | M2–M4 не измеряются, остаются M5, M6 и показатель M1 по экспертной сверке |

## Definition of Ready

- [ ] Пользователь и его роль определены
- [ ] Ценность описана в одну фразу
- [ ] Критерии приёмки сформулированы и проверяемы
- [ ] Зависимости от других историй перечислены
- [ ] Уровень автоматизации выбран и согласован с TO-BE
- [ ] Понятно, где история создаёт риск для человека

## Definition of Done

- [ ] Реализация проходит все критерии приёмки
- [ ] Для L1 и выше существует лог решения с объяснением
- [ ] Есть тест на граничные и ошибочные сценарии
- [ ] Права доступа настроены по ролям
- [ ] Документация для пользователя обновлена
- [ ] История просмотрена другим членом команды
- [ ] Риски ИИ для этой истории перепроверены, контрмеры работают

выдумано, решение в TO-BE без требования не будет реализовано.
